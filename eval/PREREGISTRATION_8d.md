## 1. Question and the claim this can support

> Does outcome-attributed trust (`memoire_feedback`, trial_cap 1, tagged notes) improve a coding agent's pass rate over
> plain cosine-top-3 memory (`plain_vector`) on conflicting lessons, with the same model, tasks and store scope?

What a result can and cannot say:

- One model (the pinned Gemini id in section 2), one bank, lessons written by this project that contain the answer.
  It measures retrieval and trust under conflicting lessons, **not** general agent improvement and not other models.
- The unit of analysis is the **family** (n = 8). The four sessions of a family re-skin one choice, so 32 tasks are not 32
  independent observations. Section 4 shows what n = 8 can and cannot resolve.
- The dev pilot (5 families, `gemini-3.1-flash-lite`) did not separate the arms: B 14/20, C0 12/20, C1-plain 12/20,
  C1-tagged 13/20, with all differences within one to two tasks. The likely outcome here is "not distinguishable". That is a valid result.

## 3. Endpoints and decision rule

All contrasts are paired by family: per-family accuracy = pass rate over the window's sessions (and over seeds),
differences taken within family. The window `s1-s4` is all four sessions.

**Primary (the only inferential test).** `Delta = accuracy(C1-t1) - accuracy(B)` over `s1-s4`.
Decision test: **exact two-sided paired sign-flip permutation test on the actual per-family differences, alpha = 0.05.**

- It is **two-sided** on purpose: "C1 is worse than plain vector" is a registered outcome, not just "C1 is better". A one-sided test
  (`H1: C1 > B`) is not used. This is stated here because 7 of 8 families improving gives p = 0.0703 two-sided but 0.0352 one-sided.
- p is computed from the magnitudes of the differences, not from counts. The table below is the equal-magnitude special case
  (generated by `exact_sign_flip_p`; zero differences are dropped, so "n" is the number of non-tied families).
- There is **no** extra "at least k of 8 families" rule. The exact p already encodes it. The family tally is reported, descriptively.

| non-tied families | positive | p two-sided | p one-sided (not used) |
|---|---|---|---|
| 8 | 8/8 | 0.0078 | 0.0039 |
| 8 | 7/8 | 0.0703 | 0.0352 |
| 8 | 6/8 | 0.2891 | 0.1445 |
| 7 | 7/7 | 0.0156 | 0.0078 |
| 7 | 6/7 | 0.1250 | 0.0625 |
| 6 | 6/6 | 0.0312 | 0.0156 |
| 6 | 5/6 | 0.2188 | 0.1094 |

With unequal magnitudes the result can differ: seven families at +0.25 and one at -0.0625 give p = 0.0156.

**Gate (descriptive screen, evaluated first).** `A` pooled pass rate in [0.15, 0.45] (the `eval/README.md` target) **and**
`mean(B) - mean(A) >= 0.15`. If the gate is not passed the bank/prompt is not informative about memory: the primary effect is
reported, no inference is drawn. (`summarize` prints Arm A against a looser `(0.1, 0.7)` constant; that is a pre-existing display
setting and is not the gate.)

**Verdict (computed by `analyze`):**

| Condition | Verdict |
|---|---|
| gate passed, p < 0.05, Delta > 0 | `supported (this bank, this model)` |
| gate passed, p < 0.05, Delta < 0 | `worse (this bank, this model)` |
| gate passed, otherwise | `not_distinguishable at this sample size` |
| gate not passed | `gate_not_passed: effect reported descriptively, no inference` |
| any registered cell missing | `incomplete` |

**What gets written for each verdict.** `supported`: "on this bank and model, C1 beat plain vector"; nothing broader.
`worse`: reported as is, and the README does not claim an accuracy advantage. `not_distinguishable`/`gate_not_passed`:
no accuracy-improvement claim anywhere (README, registry listings, release notes); positioning rests on properties that
do not depend on this test (local, no LLM extraction cost, shared across MCP clients, a mechanism that demotes notes that
fail). An interval including zero is not evidence of no effect.

**Secondary (descriptive only: effect, family-bootstrap interval, family tally; `p_exact_two_sided` is `None` by construction).**
`C1-t1 - A`, `C1-t1 - C0-t1` (s1-s4 and s3-s4), `C1-t1 - B` (s3-s4), `C0-t1 - B` (s1-s4, s1-s2),
`C0-t3 - C0-t1` (s1-s2), `C0-t3 - B`, `C1-t3 - B`, `C1-t3 - C0-t3` (s1-s4, s3-s4), `B-nopoison - B` (s2-s4, s1-s4).
The `s3-s4` window is dev-informed (feedback cannot act before s2; in the pilot the s1-s2 gap tracked exposure, not trust),
so it is labelled exploratory. The percentile bootstrap over 8 families is anti-conservative (section 4); it is an interval
for description and is never used to decide.

**Poison metrics (descriptive; `used_keys` is the model's self-report, not a causal attribution).** For sessions at or after
the poison session: poison exposure rate, failure rate given poison shown, count of failures with poison declared,
and poison exposure in the last session.
**Poison harm** = `accuracy(B-nopoison) - accuracy(B)` over s2-s4 (positive means poison hurts). It includes displacement:
with poison B shows the top 3 of 4 lessons, without it B shows all 3. At s1 the two stores are identical, so s1 prompts
must be byte-identical (an integrity check); any s1 outcome difference there is pure API noise on the same input, and is
reported as the noise floor.

## 4. What n = 8 can resolve (planning aid, `python -m eval.power_sim`)

**[Simulation, assumptions in `eval/power_sim.py`: near all-or-none families with mean 0.70, family-level effect SD 0.2, replicates only
help if reruns are stochastic.]** Realized effect = true mean accuracy difference after ceiling clipping.

| families | replicates | realized effect | exact-test power | bootstrap CI excludes 0 | mean CI width |
|---|---|---|---|---|---|
| 8 | 1 | 0 (null) | 0.00 (false positive) | 0.10 (false positive) | 0.26 |
| 8 | 1 | 0.04 / 0.10 / 0.14 | 0.01 / 0.01 / 0.02 | 0.12 / 0.24 / 0.41 | ~0.32 |
| 8 | 3 | 0 (null) | 0.01 (false positive) | 0.12 (false positive) | 0.16 |
| 8 | 3 | 0.04 / 0.10 / 0.14 | 0.03 / 0.10 / 0.20 | 0.17 / 0.37 / 0.68 | ~0.25 |
| 16 | 3 | 0.04 / 0.10 / 0.14 | 0.08 / 0.40 / 0.77 | 0.18 / 0.58 / 0.87 | ~0.18 |

Reading: with 8 families the exact test almost never rejects unless the effect is large and unanimous, and the bootstrap rejects
~10% under a true null. So `not_distinguishable` is the expected outcome for any effect near the pilot's. The interval, the
family tally and the poison metrics are the informative output; a negative or null result is reported as such.

## 5. Seeds: dev preflight decides one or two

At `temperature 0.0` and without an API seed (Google's endpoint rejects it), replicate seeds differ only through API nondeterminism.
Preflight (dev, ~42 attempts): rerun `B` and `C1-t1` (tagged) at `seed 1` into the same pilot files, then
`python -m eval.run_eval analyze --split dev --preflight --results ...`.

Rule (fixed here): **flips = tasks whose pass/fail differs between seed 0 and seed 1, pooled over B and C1-t1 (40 paired cells).**
`flips <= 1` -> **one seed (seed 0)** on `test`; `flips >= 2` -> **two seeds (0 and 1), one seed per day**. C1 flips include knock-on
effects of feedback divergence; they are counted as is.
The `test` run additionally yields the B vs B-nopoison s1 comparison (32 identical-input pairs per seed) as a second noise estimate.

Preflight commands (dev only; flags must equal those of the seed-0 runs, because the run fingerprint covers them. Exit code 3 with
"different settings" means a flag differs; exit code 4 means `--max-calls` was reached, so rerun the same command):

```powershell
$M      = "gemini-3.1-flash-lite"                       # the exact string used in the pilot
$env:GEMINI_API_KEY = "<key>"
$DEV_B  = "eval/results/dev_b_family.jsonl"
$DEV_C1 = "eval/results/dev_c1_tagged.jsonl"
$PRE    = @("--split","dev","--model",$M,"--temperature","0.0","--top-k","3","--store-scope","family",
            "--admission","admit_all","--rpm","13","--max-tokens","4096","--max-calls","80","--seeds","1")
python -m eval.run_eval run @PRE --arms B  --out $DEV_B
python -m eval.run_eval run @PRE --arms C1 --trial-cap 1 --prompt-policy tagged --out $DEV_C1
python -m eval.run_eval analyze --split dev --preflight --results $DEV_B $DEV_C1 --out eval/results/preflight.json
```

Preflight outcome (owner fills after running, before tagging): `flips = 0 / 40 (B: 0/20, C1-t1: 0/20) -> ONE seed (seed 0)`.

## 6. Integrity, exclusions, stopping

- `analyze` exits 1 and prints `integrity: FAILED` if: `split` is not `test`; `store_scope` is not `family`; `admission` is not `admit_all`;
  `model`, `model_returned`, `temperature` or `top_k` vary across registered conditions; a file mixes run fingerprints;
  any registered family/session/seed cell is missing; `B-nopoison` ever shows a poison lesson; B and B-nopoison s1 prompts differ.
- Runs with no code block or truncation (`finish_reason=length`) stay in the data as failures and are counted per condition
  (warning above 5%). There are **no post-hoc exclusions**.
- Re-running is allowed only after infrastructure failures (`run_eval` exit 3 or 4) and only by resuming the same command (same `--out`).
  Re-running or editing anything because of an outcome is prohibited. A condition's JSONL is never deleted or replaced.
- If `model_returned` changes mid-run, `analyze` reports it as an integrity failure; the data are kept and the change is reported, not merged silently.
- No tracked file may differ from the tag while running (section 8 check).
- Stopping rule: all seven conditions complete for the pre-decided seeds; no interim looks at accuracy. (`summarize` is for completion
  checks only; read pass counts after the last condition is done.)

## 7. Budget and schedule

Observed telemetry on this model (user-reported, Nov 22-23): 261 requests, 0 x 429, ~5.4% transient 503 recovered by retry,
~750 input / ~140 output tokens per request. Attempts = tasks / (1 - 0.054) = tasks x 1.057. RPD is the binding limit (~500 reported); `--rpm 13` paces ~237 attempts in about 18 minutes.

| Block | Tasks | Attempts |
|---|---|---|
| Dev preflight (B and C1-t1, seed 1) | 40 | ~42 |
| `test`, one seed (7 conditions x 32) | 224 | **~237 (1 day)** |
| `test`, two seeds | 448 | ~474 (2 days, ~237/day) |

A day-block is all seven conditions for the **same seed**, in the fixed order of section 9, so day-to-day model drift is balanced across arms and no
arm-seed is split across days. Tokens: ~0.21M per seed.

## 9. Commands

Common arguments (`$M` is `<MODEL_ID>`; `--max-calls 80` is a per-process safety net, a condition resumes by rerunning the same command):

```powershell
$M     = "gemini-3.1-flash-lite"
$SEEDS = "0"          # "0" on day 1; "1" on day 2 only if the preflight says TWO
$COM   = @("--split","test","--allow-test-split","--model",$M,"--temperature","0.0","--top-k","3",
           "--store-scope","family","--admission","admit_all","--rpm","13","--max-tokens","4096","--max-calls","80")
function Run-Cond($name, [string[]]$extra) {
  do {
    python -m eval.run_eval run @COM --seeds $SEEDS @extra --out "eval/results/test_$name.jsonl"
    $code = $LASTEXITCODE
  } while ($code -eq 4)
  if ($code -ne 0) { throw "run_eval exited $code for $name" }
}
Run-Cond "A"          @("--arms","A")
Run-Cond "B"          @("--arms","B")
Run-Cond "B_nopoison" @("--arms","B","--no-poison")
Run-Cond "C0_t1"      @("--arms","C0","--trial-cap","1","--prompt-policy","tagged")
Run-Cond "C1_t1"      @("--arms","C1","--trial-cap","1","--prompt-policy","tagged")
Run-Cond "C0_t3"      @("--arms","C0","--trial-cap","3","--prompt-policy","tagged")
Run-Cond "C1_t3"      @("--arms","C1","--trial-cap","3","--prompt-policy","tagged")
```

Analysis (after all conditions and seeds are complete; reads files only, no model calls):

```powershell
python -m eval.run_eval analyze --split test --results (Get-ChildItem eval/results/test_*.jsonl | ForEach-Object FullName) --out eval/results/test_report.json
```

The seed-count rule (section 5) decides `$SEEDS`; the preflight commands are in section 5.
